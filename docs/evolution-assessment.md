# csCore — Evolution Assessment

Status: draft for discussion · Date: 2026-11-15 · Scope: library at `dev` @ `74d2f0a`

csCore is the base library of csfoundation: every other cs library depends on
it. This document describes what it contains, what is actually used, its
problems, and options for how to reshape it (slimming, renaming, growing).
Ideas for new content will be added later; §6 lists the needs already visible
from the csLie and csVisOpenGL assessments.

---

## 1. What csCore contains

csCore is organized as one CMake package with independent components. All of
them are header-only (`INTERFACE`) except `math` (static).

| Component | Kind | Content | Size |
|-----------|------|---------|------|
| `assert` | **own** | leveled asserts: a CMake generator that writes a per-project header (`<PROJECT>_ASSERT_{RELEASE,RELWITHDEBINFO,DEBUG,PARANOID,SAFE_MATH}`), enabled per build configuration, built on libassert | ~320 lines (CMake + template) |
| `core` | **own** | `float32_t` / `float64_t` aliases, IEEE-754 static checks, type traits | 30 lines |
| `math` | **own** | `degToRad`, `radToDeg`, `wrapToPi`, `angleDistance` (float/double, explicit instantiations) | 90 lines + tests |
| `eigenUtils` | **own** | matrix shape checks, rotation-matrix and isometry validation | 180 lines + tests |
| `testUtils` | **own** | Catch2 + libassert glue (`REQUIRE_NO_ASSERT`) | 25 lines |
| `format` | alias | 15 headers that include the matching fmt header; `csCore::format` = `::fmt` | wrapper only |
| `formatEigen` | alias | fmt-eigen | wrapper only |
| `language` | alias | `tl::optional`, `tl::expected` via `using namespace ::tl` | wrapper only |
| `namedType` | alias | NamedType (`fluent::`) as `csCore::namedType` | wrapper only |
| `pipes` | alias | joboccara/pipes, 40 headers generated by a script | wrapper only |

About half of the ~8 kLOC in the repository are **tests copied from upstream
projects** (tl-optional/expected, NamedType, pipes) with namespaces replaced.

Third-party dependencies pulled in by csCore (from `csfoundation_config.py`):
eigen3, Catch2, fmt 11.2, fmt-eigen, libassert 2.1, pipes, NamedType,
tl-expected 1.0, tl-optional 1.2.

## 2. What is actually used

Searched in csLie, csCamera, csVisOpenGL, csImgTracker, csSkiTracker,
csoptimization, csopencvcpu and csopencvcuda:

| Component | Used by |
|-----------|---------|
| `assert` | csLie, csCamera, csVisOpenGL, csImgTracker, csSkiTracker, csoptimization |
| `core` | csLie, csCamera, csVisOpenGL, csImgTracker, csoptimization |
| `eigenUtils` | csLie, csCamera, csVisOpenGL, csImgTracker, csoptimization |
| `testUtils` | csLie, csCamera, csoptimization |
| `math` | csLie (tests), csoptimization |
| `format`, `formatEigen`, `language`, `namedType`, `pipes` | **nobody** |

So csCore is really **assert + basic types + Eigen checks + a few angle
helpers + test glue**. The five alias components and their five third-party
dependencies are unused. They are still built, tested and installed in every
setup.

## 3. Assessment of each part

### 3.1 `assert`: the most valuable piece

**What is good.** Five assert levels with a clear cost model (documented in the
generated header), enabled per configuration, configurable per project through
CMake cache options, and libassert's excellent diagnostics. The `Paranoid`
configuration with `PARANOID` and `SAFE_MATH` checks is a real strength of the
whole foundation.

**Problems:**

1. **Boilerplate in every consumer.** Each library repeats ~10 lines: find the
   `assert` component, append the module path, `include(csAssert)`, five
   `csSetAssertDefaultOnForConfig` calls, `csAssertGenerateProject`,
   `list(POP_BACK ...)`. These should be one call.
2. **CMake naming is inconsistent** with csCMake: `csAssertGenerateProject` /
   `csSetAssertDefaultOnForConfig` (camelCase) vs `cs_add_library` /
   `cs_target_*` (snake_case).
3. **The cache uses `FORCE`**, so changing a default requires deleting the build
   directory (documented in the CMake file, but easy to forget).
4. **Depends on a libassert implementation macro.** The generated macros call
   `LIBASSERT_INVOKE(...)` directly. It is what libassert's own `DEBUG_ASSERT`
   expands to, but it is not documented public API and may change in a libassert
   upgrade. All levels also report as `"DEBUG_ASSERT"` in failure messages, so a
   failing `PARANOID` check is not identified as such.
5. **Not usable on GPU / in device code** (libassert needs host runtime and
   exceptions or abort handlers). This is required by the csLie GPU plan.
6. **No tests** for the generator (single- and multi-config, option overrides).

### 3.2 `core`

- `float32_t` / `float64_t` are declared in the **global namespace**. Since
  C++23, `<stdfloat>` defines `std::float32_t` / `std::float64_t` as *distinct*
  extended floating types (not aliases of `float`/`double`). This is harmless
  today, but confusing once C++23 is in use, and clashes under `using namespace std`.
  Consider moving them into `csCore::` (with a transition alias) or documenting the difference.
- The IEEE-754 and size `static_assert`s are good. Keep them.
- The component name `core` inside `csCore` (`csCore::core`) is redundant.

### 3.3 `math`

- A **static library for four trivial functions**, explicitly instantiated for
  float/double. This blocks inlining and constant folding at call sites. Make it
  header-only (`inline` / `constexpr` where possible).
- Uses `M_PI` via `_USE_MATH_DEFINES`, which needs a Windows-Clang compile-option
  workaround in its CMake. A `constexpr` pi per type (or C++20
  `std::numbers::pi_v<T>`) removes both. csLie already defines its own
  `Constants<S>::pi`, so the two should be unified here.
- `wrapToPi` = `atan2(sin x, cos x)`: accurate for any |x|, but 3 transcendental
  calls. `angleDistance` uses 4 trig calls + `atan2`; `wrapToPi(target − reference)`
  gives the same result for finite inputs at about half the cost.
  Document range conventions (−π, π] and behaviour at exactly ±π.

### 3.4 `eigenUtils`

- Useful and used everywhere (shape checks behind asserts, rotation/isometry validation).
- **Wrong assert messages**: `isValidRotationMatrix3D` says "rot required to be
  2x2"; `isValidIsometryMatrix2D` says "transf required to be 4x4".
- `isValidRotationMatrix` checks both `R·Rᵀ = I` and `Rᵀ·R = I`. For square
  matrices one implies the other up to rounding, so the second is redundant work
  (minor, debug-only cost).
- The tolerance is Eigen's `dummy_precision` (1e-12 double, 1e-5 float) applied
  to determinant and orthogonality equally. That is fine for asserts; document it.
- Overlap with csLie: validity checks for SO3/SE3 belong conceptually to csLie.
  Keep the generic matrix checks here (shape, finite, symmetric, …) and let csLie
  own group-specific validation if csLie grows its own types.

### 3.5 `testUtils`

- **Bug**: `REQUIRE_NO_ASSERT` installs a throwing failure handler and restores
  the old one only on the success path. When the expression asserts, `FAIL(...)`
  throws out of the macro and the throwing handler **stays installed** for all
  following tests (the same happens if the expression throws anything else).
  Fix with an RAII guard that restores the handler in its destructor.
- Good place for the **precision helpers** needed by csLie (error in ε/ulps,
  extended-precision comparisons) and for golden-image helpers needed by csVisOpenGL.

### 3.6 The alias components (`format`, `formatEigen`, `language`, `namedType`, `pipes`)

Idea behind them: one indirection point (`csCore::format`, `csCore::language`, …)
so the implementation can later be swapped (e.g. to `std::format`, `std::expected`)
without touching client code.

| Component | Worth keeping? | Reason |
|-----------|---------------|--------|
| `format` (fmt) | **yes, if a logging/printing need is planned** | fmt is the reference implementation; `std::format` (C++20) and `std::print` (C++23) are subsets. Useful for asserts/messages/logging |
| `formatEigen` | together with `format` | small; printing Eigen types is common in debugging |
| `language` → `expected` | **yes** | `tl::expected` is the best C++17 error-handling vocabulary until C++23 `std::expected`; needed for "checked" APIs (csLie `std::optional`/`expected` variants) |
| `language` → `optional` | weak | `std::optional` is already C++17; `tl::optional` only adds monadic ops and `optional<T&>`. Also, `using namespace ::tl` pulls every `tl` name into `csCore::language` |
| `namedType` | maybe | strong types are a good idea (recommended in csLie and csVis assessments), but NamedType's activity is low (verify); a small own `StrongType<T, Tag>` may be simpler |
| `pipes` | **no** | experimental library with low activity (verify); C++20 ranges / range-v3 cover the use cases; 40 generated headers + copied tests to maintain |

Regardless of the decision:

- **Do not copy upstream tests.** Upstream already tests its code. Keep one small
  compile/smoke test per alias that checks the alias works.
- **Do not mirror every upstream header** (15 for fmt, 40 for pipes). One umbrella
  header per component, or a CMake-provided include of the upstream path, is enough.
- **Make unused aliases optional components** so a csfoundation setup does not
  have to fetch and build their dependencies.

## 4. Slim, rename, or both?

### 4.1 Options

| Option | What changes | Pros | Cons |
|--------|--------------|------|------|
| **A. Keep as is** | nothing | no work | 5 unused deps, copied tests, inconsistent names |
| **B. Slim** | drop `pipes`; make `format`/`formatEigen`/`namedType`/`optional` optional (off by default); delete copied tests | faster setup and CI; less to maintain | none for current users (nobody uses them) |
| **C. Slim + rename components** | B, plus clearer component names | coherent naming before the library grows | breaks includes/targets in 6 consumer projects (needs a transition period) |
| **D. Move assert generation into csCMake** | csCMake gets a generic "leveled feature header" generator; csCore keeps the libassert-based macros | assert setup becomes a one-line csCMake call for every project | couples csCMake to a convention; csCMake stays dependency-free only if the generator stays generic |

### 4.2 Recommendation

**B now, C with the next breaking release, and D evaluated together with the
boilerplate fix (§3.1-1).**

Suggested names for option C:

| Today | Proposed | Note |
|-------|----------|------|
| `csCore::core` (`BasicTypes.hpp`) | `csCore::types` | merge `expected` (and a strong-type helper) here: "vocabulary types" |
| `csCore::language` | merged into `csCore::types` | `optional` dropped in favour of `std::optional` |
| `csCore::eigenUtils` | `csCore::eigen` | plus Eigen formatting (today `formatEigen`) |
| `csCore::math` | `csCore::math` | header-only; constants, angles, math traits (§6) |
| `csCore::assert` | `csCore::assert` | unchanged name; simpler CMake API |
| `csCore::testUtils` | `csCore::test` | precision and golden-image helpers |
| `csCore::format` | `csCore::format` | optional component |
| `csCore::pipes` | removed (done 2026-11-16, with pipes in third_party_base_libs) | |

Transition: keep the old targets as `ALIAS`es and the old headers as forwarding
headers for one release, with a deprecation note.

### 4.3 Growth: merge csLie in, or split asserts out?

csCore is expected to grow with shared utilities (the standard way to manage
properties, serialize/deserialize, and so on). Two questions follow: should
csLie move into csCore, and should asserts become their own library so that
csLie does not depend on a growing csCore?

**Recommendation: neither. Keep csCore as one repository with two layers, keep
csLie separate, and declare dependencies per component.**

| Layer | Components | Rules |
|-------|------------|-------|
| **base** | `assert`, `types`, `math` (traits, constants), `eigen`, host/device macros | header-only; usable on GPU device code and MCU-class targets (no exceptions/allocation required); third-party: libassert only, and swappable (§3.1) |
| **utilities** | `properties`, `serialization`, `format`, `logging`, … | may have heavier third-party dependencies (JSON/YAML, fmt, …); each is optional |
| **test** | `test` | test-only helpers |

Rules: base never depends on utilities; foundation math libraries (csLie,
csCamera) depend on base only.

Why not split `assert` into its own repository: csCore is already split into
components at the CMake level. csLie links only `assert`, `core` and
`eigenUtils` today, so it would not link properties or serialization later
either. A separate repository adds release and versioning overhead, which is
exactly the "too many small libraries" problem, and solves nothing the layering
does not solve.

Why not merge csLie into csCore: csLie has its own goals (precision suite,
benchmarks, SIMD/GPU, possibly a public release), its own optional dependencies
(xsimd, CUDA) that must not land in every csCore consumer, and its own release
cadence. Merging makes sense when two libraries share dependencies and cadence,
and these do not. Within csfoundation a separate repository costs almost nothing.

**The real coupling is dependency fetching, not repositories.** Today
`csfoundation_config.py` declares third-party dependencies per library, so
csCore's whole list is downloaded and built for every consumer. Once a
serialization component brings in a JSON/YAML library, every csLie build would
pull it too. Fix: declare third-party dependencies **per component** (or make
the utility components optional, off by default), so that a consumer of the base
layer fetches only libassert.

## 5. Cross-cutting decision: the C++ standard

The whole foundation is C++17, which is a fully reasonable baseline: every
current desktop, embedded Linux and microcontroller toolchain (STM32 GCC/Clang,
ESP-IDF, ChibiOS projects) supports it; the only notable exception is CUDA
device code on JetPack 4 Jetsons (CUDA 10.2). Several csCore items exist only to
fill C++17 gaps:

| Need | C++17 (today) | C++20 | C++23 |
|------|---------------|-------|-------|
| constants (pi) | `M_PI` / own | `std::numbers` | |
| span (batch APIs in csLie/csVis) | gsl / span-lite / own | `std::span` | |
| concepts (scalar-generic kernels) | SFINAE | ✅ | |
| formatting | fmt | `std::format` | `std::print` |
| error handling | tl::expected | | `std::expected` |
| ranges | pipes / range-v3 | `std::ranges` | |
| fixed-width floats | own `float32_t` | | `<stdfloat>` |

Moving to **C++20** would remove `M_PI` hacks, give `span` and concepts (very
useful for the csLie kernel design), and make `pipes` obviously redundant.
Compiler support: GCC ≥ 10, Clang ≥ 10, MSVC 2019 16.10+, and NVCC ≥ 12 for
CUDA code (to verify against the toolchains used by csCMake presets).
The decision affects every cs library, so it belongs to csfoundation as a whole.

## 6. Needs already visible from the other assessments

Candidates for csCore because more than one library needs them:

| Item | Needed by | Notes |
|------|-----------|-------|
| `CSCORE_HD` (host/device annotation) + **device-safe asserts** | csLie, csCamera, csVisOpenGL CUDA interop | asserts compile out or trap on device |
| **Math traits** (`sqrt`, `rsqrt`, `sincos`, `atan2`, `select`, `fma`) for float, double, SIMD batch, Jet, CUDA | csLie kernels, csCamera projection | single place that fixes the "float promoted to double" class of bugs |
| **Typed constants** (`pi<T>`, `eps<T>`, Taylor thresholds helpers) | csLie, csCamera, math | replaces `M_PI` and csLie `Constants` |
| **Span / strided view** types | csLie batch API, csVis data sources | `std::span` if C++20 |
| **ImageView** (non-owning width/height/stride/format/data) | csVisOpenGL, csCamera, csImgTracker | decouples from QImage / cv::Mat |
| **Precision test helpers** (ε/ulp error, extended-precision reference compare) | csLie precision suite, csCamera | in `test` |
| **Benchmark helpers** | csLie, csCamera | thin wrapper or just a dependency convention (Google Benchmark / nanobench) |
| Optional **logging** on top of fmt | apps (trackers) | only if a real need appears |

## 7. Fixes independent of any decision

- `REQUIRE_NO_ASSERT`: restore the failure handler with RAII (§3.5).
- Wrong assert messages in `RotationMatrix_impl.hpp` and `IsometryMatrix_impl.hpp` (§3.4).
- Generated asserts: report the real level name in messages (§3.1-4).
- `math`: header-only, typed constants, drop the `_USE_MATH_DEFINES` workaround (§3.3).
- README: describe components, the assert levels and the Paranoid configuration
  (today it only holds a clang-tidy TODO).
- Add tests for the assert generator.

## 8. Proposed roadmap

**Phase 0: Fixes.** The items of §7.

**Phase 1: Slim (option B).** Remove `pipes`; make the other aliases optional
components (off by default in csfoundation setup); delete copied upstream tests,
keep one smoke test per alias; one umbrella header per alias.

**Phase 2: Assert ergonomics.** One-call CMake API (`cs_assert_generate(...)`
style, possibly provided by csCMake, option D); level names in messages;
device-safe fallback; generator tests.

**Phase 3: Shared foundations for csLie / csVis / csCamera (§6).** Host/device
macro, math traits, typed constants, span/ImageView, precision test helpers.

**Phase 4: Rename (option C)**, with forwarding headers and target aliases for
one release. Combine it with the C++20 decision if taken.

## 9. Summary

- csCore is in practice **assert + basic types + Eigen checks + angle helpers +
  test glue**. Five alias components (fmt, fmt-eigen, tl, NamedType, pipes) are
  **unused** but still fetched, built and tested, and copied upstream tests make
  up about half the repository.
- The **leveled assert system** is the most valuable piece. It needs a simpler
  CMake API, proper level names, independence from libassert internals and a
  device-safe variant.
- Small but real defects: a test macro that leaks its failure handler, wrong
  assert messages, a static library for four trivial functions, `M_PI` workarounds.
- Recommended: **slim now, rename at the next breaking release**, and make csCore
  the home of the shared pieces csLie and csVisOpenGL will need (host/device
  macros, math traits, constants, views, precision test helpers).
- The **C++17 → C++20** question affects all cs libraries and would remove several
  of the gaps csCore fills today.
- **Growth model**: one repository with a **base** layer (assert, types, math
  traits, Eigen helpers; header-only, GPU/MCU safe) and optional **utility**
  components (properties, serialization, …). csLie stays separate and depends on
  base only. Third-party dependencies are declared per component (§4.3).
